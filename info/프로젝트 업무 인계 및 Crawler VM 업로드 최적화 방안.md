## **1\. 현 상황 및 Context 분석**

* **현재 상태**: 프로젝트 종료 임박, 업무 인계 필요. 신규 코딩보다는 \*\*"정리 및 실행 가능한 상태"\*\*로 만드는 것이 목표.  
* **Git 이슈**: `Source Control` 탭의 378개 변경 사항은 주로 **폴더명 변경**(예: `naver_blog` \-\> `3_naver_blog`)으로 인해 기존 폴더들이 "삭제(Deleted)"되고, 새 이름의 폴더들이 "추적되지 않음(Untracked)"으로 인식되었기 때문입니다.  
* **구조적 차이**:  
  * **본인(Kimble)**: `data`, `logs`, `config` 등으로 폴더가 잘 구조화되어 있음. 그러나 파일명에 버전(v10, v11)을 명시하여 Git의 기능과 중복됨.  
  * **동료**: 폴더 구분 없이 단일 디렉토리에 파일이 평면적으로 배치됨. 그러나 실행 파일명은 단일화되어 있어 진입점이 명확함.

## **2\. 구조 평가 및 개선 제안 (Task 2 & 3\)**

인계받는 사람이 즉시 작업을 시작할 수 있도록, \*\*"본인의 폴더 구조(Good)"\*\*와 \*\*"동료의 파일 명명 규칙(Good)"\*\*을 결합하는 하이브리드 방식을 제안합니다.

### A. 폴더 및 파일 구조 (Comparison & Optimization)

| 구분 | 본인 스타일 (1\~4번 폴더) | 동료 스타일 (5\~7번 폴더) | 최적 제안 (Recommendation) |
| :---- | :---- | :---- | :---- |
| **폴더 구조** | `data/`, `logs/`, `archive/` 등 기능별 분리 **(우수)** | root에 모두 혼재 | **본인 스타일 채택**. 데이터와 소스 코드는 분리되어야 관리 및 인계가 쉽습니다. |
| **파일 버전** | `...v10.py`, `...v11.py` 혼재 | `...crawling.py` 하나만 존재 **(우수)** | **동료 스타일 채택**. 인계자는 "무엇을 실행해야 하는지"가 명확해야 합니다. |
| **설정 관리** | config.py,  .env 사용 **(우수)** | 코드 내 하드코딩 추정 | **본인 스타일 유지**. 보안 및 환경 설정을 위해 설정 파일 분리는 필수입니다. |

### B. 선임 개발자 피드백 반영 (Versioning)

* **피드백**: "Git이 있는데 왜 파일명에 버전을 붙이는가?" \-\> **정확한 지적입니다.**  
* **이유**: Git은 "시간 여행" 도구입니다. 언제든 과거 커밋으로 돌아갈 수 있습니다. 파일명에 버전을 붙이면, 인계받는 사람은 "v11이 최종인가? v10에 있는 기능이 v11에 빠진 건 아닌가?"라고 혼란스러워합니다.  
* **해결책**:  
  1. 가장 안정적인 최신 버전(`v11`)을 **`main.py`** 또는 \*\*`crawler.py`\*\*로 이름을 변경합니다.  
  2. 과거 버전(`v10` 등)이나 참고용 파일은 과감하게 **`archive/`** (또는 `legacy/`) 폴더로 이동시킵니다.  
  3. `data/` 폴더 내의 수많은 CSV/JSON 결과물은 **Git에 올리지 않는 것**이 원칙입니다(용량 및 보안 문제). 샘플 데이터 1\~2개만 남기고 나머지는   
  4. .gitignore로 제외하거나 별도 아카이브(zip)로 전달해야 합니다.

### C. Source Control (Git) 378개 변경 사항 처리

* **정체**: 앞서 언급했듯 `naver_blog` 폴더가 사라지고 `3_naver_blog`가 생긴 것을 Git이 아직 "이동(Rename)"으로 인식하지 못하고 "삭제 \+ 생성"으로 보고 있기 때문입니다.  
* **처리 방안**:  
  1. 불필요한 데이터 파일(수십 MB짜리 JSON 등)을   
  2. .gitignore에 등록하여 변경 목록에서 제외합니다.  
  3. 나머지 모든 변경 사항을 `git add .` (Stage) 하면, Git이 자동으로 "아, 내용이 같으니 이름이 바뀐 것이구나"라고 인식하여 `Renamed` 상태로 정리해 줄 것입니다.

## **3\. Crawler VM 업로드 및 인계 절차 (Task 3\)**

"VM에 업로드 한 후 Git 커밋"보다는 \*\*"로컬 정리 \-\> Git 커밋 \-\> VM에서 Pull"\*\*이 정석적인 개발자 인계 방식입니다.

### \[단계별 실행 가이드\]

#### Step 1: 로컬 정리 (The Cleanup)

1. **파일명 통일**: 각 폴더(`1_band` \~ `4_youtube`)의 최신 실행 파일을 `main.py` 또는 `crawler.py`로 이름 변경. 구버전은 `archive/`로 이동.  
2. **동료 폴더 정리**: `5_kakaostory` 등도 가능하다면 `logs/`, `data/` 폴더를 만들어 파일을 분류 (시간이 없다면 최소한 소스코드와 데이터 파일이라도 분리).  
3. **데이터 제외**:   
4. .gitignore 파일을 점검하여 `*.csv`, `*.json`, `*.log`가 Git에 올라가지 않도록 설정 (단, 인계용 샘플 데이터는 예외).

#### Step 2: Git 동기화 (Source Control)

1. **Stage All**: `Source Control` 탭에서 `+` 버튼(또는 `git add .`)을 눌러 변경 사항을 스테이징 영역으로 올립니다. 378개 숫자가 줄어들거나 `R`(Rename) 상태로 바뀔 것입니다.  
2. **Commit**: "Refactor: 폴더 구조 재편 및 인계 준비 완료" 메시지로 커밋합니다.  
3. **Push**: 원격 저장소(GitHub/GitLab 등)에 푸시합니다.

#### Step 3: VM 배포 (Deployment)

* **Best Practice**: Crawler VM에 접속하여 `git clone (주소)` 또는 이미 있다면 `git pull`을 입력합니다. 이렇게 하면 로컬에서 정리한 깔끔한 최신 상태가 그대로 VM에 복제됩니다.  
* **Alternative (수동 업로드)**: Git 사용이 어렵다면, 로컬 프로젝트 폴더 전체를 압축하되, **`.git`, `.venv`, `__pycache__` 폴더와 `data` 폴더의 대용량 파일들은 제외**하고 압축하여 VM에 업로드합니다.

1\. 과거 버전 파일 처리 (Archive vs Delete)

"Git Tag(태그)" 기능을 사용하는 것이 최적의 방안입니다.

* 이유: 말씀하신 대로 v10, v11을 남겨두는 것은 인계자에게 혼란을 줍니다("어떤 게 진짜 최종이지?"). 하지만 단순히 지우는 것도 불안하실 수 있습니다.  
* 해결책: 현재의 모든 파일(버전들 포함)을 그대로 보존하는 Git Tag를 하나 붙여두고, 메인 폴더는 깔끔하게 정리하는 것입니다.  
  * 작업 순서:  
    * git tag legacy-backup-20251211 명령어로 현재 상태에 '갈피'를 끼웁니다.  
    * 이후 v10 등을 삭제하고 v11을 main.py로 변경하여 정리합니다.  
  * 효과:  
    * 평소에는 깔끔한 최신 파일만 보입니다 (인계자 혼란 방지).  
    * 만약 과거 v10 데이터나 코드가 필요하면 언제든 git checkout legacy-backup-20251211 한 줄로 모든 파일이 삭제되기 전 상태로 완벽하게 복구되어 조회 가능합니다.

2\. 동료 작업 폴더 (Crawler VM vs Local) 비교 결과

Crawler VM에 직접 접속하여 확인한 결과, 님(Local)의 컴퓨터에 있는 파일이 훨씬 최신이고 완전합니다. VM에 있는 파일들은 예전 버전이거나 일부만 남아있습니다.

* Instagram:  
  * VM: insta\_crawl.py (구버전 추정, 파일명 다름)  
  * Local: instagram\_crawling\_userposts.py, \_ocr.py 등 기능별로 모듈화된 최신 코드 보유. (Local 승)  
* Facebook:  
  * VM: 폴더가 아예 없습니다.  
  * Local: facebook\_crawling.py 등 파일 보유. (Local 승)  
* Kakaostory:  
  * VM: crawling 파일은 없고 postprocess.py와 데이터 결과물(json)만 있습니다.  
  * Local: crawling\_test.py 등 수집 코드 포함 전체 보유. (Local 승)

결론: 동료의 작업물을 VM에서 가져올 필요 없이, \*\*현재 가지고 계신 Local 파일들을 기준으로 정리하여 VM에 덮어쓰는 것(Upload)\*\*이 올바른 방향입니다.
